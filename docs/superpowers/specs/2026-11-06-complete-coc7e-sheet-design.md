# 完整 CoC 7e 官方数值卡设计

状态：已确认（2026-11-06，包含对既有行为的明确修正）

## 1. 目标与依据

玩家工作台目前只提交姓名和背景，虽然 `PATCH /api/v1/pl/characters/:id` 已支持 `sheetData`，玩家仍无法维护人物数值。本次把玩家与 GM 的数值编辑统一到规则注册表，并按用户指定的 `/mnt/games/跑团/COC/COC7th守秘人规则书2002c.pdf` 补全官方角色卡的数值能力。

主要依据：

- 第三章“创建调查员”：PDF 24–42（印刷页 23–41）。
- 第四章“技能”：PDF 44–70，技能总表位于 PDF 47（印刷页 46）。
- 官方 1920s 角色卡样例：PDF 41–42（印刷页 40–41）。
- 信用评级与资产表：PDF 36–38（印刷页 35–37）。
- 克苏鲁神话、信用评级与 SAN 上限：PDF 51（印刷页 50）。
- 技能成长、奖励骰与超过 100%：规则书 5.11。
- 本机真实半自动 Excel 模板 `/mnt/games/跑团/COC/COC七版半自动人物卡.xlsx` 仅用于验证导入布局，不视为官方规则来源。
- 产品既有的版本、审核、团内快照与 GM 状态权限原则保持不变。

## 2. 交付范围

### 2.1 主卡可编辑内容

- 八项基础属性与幸运：STR、CON、SIZ、DEX、APP、INT、POW、EDU、LUCK，整数 1–99；显示全值、半值和五分之一值。
- 建卡所需结构化资料：时代（1920s/现代）、职业、年龄（15–90）。保留现有姓名、背景与表情立绘编辑，不重建纯叙事背景系统。
- 完整标准技能、官方专攻、非常规技能和现代技能；包括数学 10%、其余科学专攻通常 1%、驾驶与汽车驾驶分离、格斗（矛）归入格斗等规则书正文勘误。
- 技能当前值允许 0–999，覆盖规则书允许的 100% 以上成长；自定义技能保存基础值与当前值，自定义专攻保存规范名称。
- 职业参考信息：规则书 25 个范例职业及自定义职业、本职技能、信用评级范围、职业技能点公式；兴趣技能点由 INT×2 推导。职业预设用于填写和核算参考，切换预设不重置技能值。
- 武器列表：名称、关联技能、伤害表达式、射程、每轮次数、装弹量、故障值、贯穿与是否应用伤害加值；关联技能的常规/困难/极难值自动显示。
- 护甲名称、护甲值、覆盖部位与可选减值。
- 装备条目及数量。
- 法术数值记录：名称、MP 消耗、SAN 消耗、施法时间与效果说明。消耗允许规则文本，以支持可变消耗。
- 神话典籍与第三类接触的数值记录：SAN 损失、克苏鲁神话增长、研读时长、关联法术/遭遇说明。它们是主卡历史记录，不自动修改任何进行中团的状态。
- 信用评级对应的六档生活水平，以及消费水平、现金、其他资产总值和资产明细；按时代与信用评级给出规则表建议值，只有用户明确操作时才填入建议值。
- 移动修正值，用于规则表之外的 GM/玩家约定调整。

### 2.2 自动推导内容

以下值由 CoC 共享规则模块的纯函数计算，前端只展示，服务端在初始化或规则动作中使用同一实现：

- 半值 `floor(value / 2)`、五分之一值 `floor(value / 5)`。
- HP 上限 `max(1, floor((CON + SIZ) / 10))`。
- MP 上限 `floor(POW / 5)`；初始 SAN 为不超过上限的 POW；SAN 上限 `99 - 克苏鲁神话`。
- 闪避基础值 `floor(DEX / 2)`，母语基础值 = EDU。
- 伤害加值与体格按 STR+SIZ 的规则表计算；每超过一个 80 点档增加 1d6 DB 与 1 体格，枪械不自动应用 DB。
- MOV 先按 STR/DEX/SIZ 得 7/8/9，等于 SIZ 的情形不得误判为 9；再应用 40–89 岁修正与显式移动修正，最终不低于 1。
- 兴趣技能点 INT×2、所选职业的技能点预算、信用评级生活水平和两时代资产建议值。
- 重伤参考阈值 `floor(maxHp / 2)`，仅作展示；实际状态仍由既有 GM 状态逻辑处理。

### 2.3 明确不做

- 玩家不能通过主卡编辑直接修改团内当前 HP、MP、SAN、伤害、疯狂、幸运消耗或其他团内状态；这些仍只由 GM 或既有规则动作修改。
- 主卡修改不自动覆盖任何已入团快照，仍由 GM 通过差异预览显式同步，且不自动追溯改写当前伤害、状态与成长。
- 不实现自动掷骰建卡、EDU 增强检定、强制职业点分配、战斗自动结算、幸运消耗、自动施法或神话典籍成长结算。
- 年龄只自动影响 MOV；其他年龄扣减和 EDU 增强次数作为建卡参考显示，不擅自扣除玩家属性。
- 不强制保存技能点来源四列；主卡以最终技能值为事实源，点数预算用于参考和可选核对。
- 不新增玩家名、性别、住地、出生地及背景十项等纯叙事字段，继续使用现有背景资料。
- 不删除旧人物、旧版本或历史团快照，不引入第二套并行人物卡业务流程，不修改关系型数据库表结构。

## 3. 方案选择

### 采用：扩展规则卡 schema，并注册共享规则编辑器

将完整字段保存在现有 `sheetJson` 中，升级 CoC schema 版本并提供旧卡的非破坏性规范化。新增字段属于 CoC 命名空间；通用人物更新协议仍只传 `sheetData`，由服务端 `RuleRegistry` 取得对应规则实现做权威校验。

客户端把数值编辑 UI 注册为 CoC 规则组件。PL 的现有编辑弹窗与 GM 的数值编辑弹窗都通过规则注册表使用同一组件，PL 保存时一次提交资料、数值和 `expectedVersion`。

优点是与现有 JSON 快照、版本、审核、成长和同步模型一致，不需要关系表迁移，也不会产生 PL/GM 两套公式或字段实现。

### 不采用：只补玩家输入框

只在 PL 弹窗添加九属性和现有技能，仍会缺专攻、战斗、职业、资产和神话数值，且容易继续复制 GM 的规则逻辑。

### 不采用：把每项数值拆成关系表

武器、技能和属性分别建表会增加快照、历史、导入和同步复杂度，但对当前单卡 JSON 聚合没有必要收益，也会扩大无关迁移范围。

## 4. 数据模型与规则边界

- 新 schema 显式记录版本；`RuleSystem` 提供必需的统一解析/规范化入口，所有当前卡、历史卡、团快照、导入和玩法读取都经过它。旧卡补齐空列表、默认时代和无修正值，保存后写为新版；历史行本身不改写。
- 保留现有技能键作为鉴定、成长和快照引用键。标准技能与常见专攻由目录给出规范键、别名和基础值；“取悦/魅惑”“导航/领航”“技艺/艺术与手艺”“步枪/霰弹枪”等映射到单一规范键。
- 只持久化玩家显式填写或导入明确提供的技能值；未出现的目录技能在读取时按基础值推导，避免保存整张目录造成版本膨胀。自定义技能与自定义专攻定义必须持久化。
- 姓名、背景与立绘仍只提升 `profileVersion`，不会使审核过期；规则卡字段变化才提升 `sheetVersion`。一次保存可以同时提升两类版本，但整体 `version` 只递增一次。
- 范围技能的总属名称不能作为可加点技能；必须选择专攻。自定义技能保存名称、基础值与当前值。删除被武器引用的自定义技能时必须阻止或先解除引用。
- 信用评级只存于 `skills['信用评级']`，资产面板读写同一个值，不新增第二个信用字段。
- 职业技能只保存预设/自定义定义及本职技能标记，不保存可重算的预算总额。
- 武器伤害、射程、次数和法术消耗保留规则文本能力；装弹量、故障值、数量、研读时长等纯数值字段做范围校验。常规/困难/极难值不重复存储。
- 资产实际值与规则表建议值分开；实际值由用户维护，建议值由信用评级和时代推导。金额允许规则表所需的小数和大数，并附货币/补充说明。
- 所有数组、文本和数值都有服务端 schema 限制，避免超大或畸形 `sheetJson`。
- `permanentSheetFields` 仍只声明九属性。PL 对自有主卡的正常编辑与 GM 终生字段审计是不同入口；GM 通过完整编辑器修改九属性时也必须产生逐字段审计，不能绕过审计。
- 规则元数据和 CoC schema 版本同步升级，所有客户端保存都从规范化后的完整草稿序列化，不得只重建 `attributes + skills` 而丢掉其他字段。

## 5. 必须修正的既有行为

这些修正会改变现有运行行为，需随本设计一起明确批准：

1. **鉴定读取团内快照**：当前玩法实际读取主卡，改为读取 `session_characters.sheet_json`。未同步的主卡编辑不再影响进行中团，消除卡面与鉴定目标值不一致。
2. **审核版本真正生效**：提交、决定和入团资格都校验现有 `character_reviews.submitted_sheet_version`。主卡变化后，旧审核保留为历史但不能再用于新入团/自动认领；待审版本已过期时不能批准，需重新提交。已有待审记录同样按版本比较，不设豁免。既有团继续使用自己的快照。
3. **官方成长规则**：技能值与成长允许超过 100%；使用奖励骰的成功不产生成长标记；信用评级与克苏鲁神话不走普通成长标记和普通成长确认，服务端与前端同时限制。
4. **官方 SAN 与 MOV 公式**：新团/新入团按 `99 - 克苏鲁神话` 初始化 SAN 上限，并修正 MOV 相等边界和年龄修正。主卡后续变化不自动改写进行中团；GM 编辑团内状态时仍使用既有入口。
5. **整卡写入门禁**：所有 UI 的整卡保存、Excel 覆盖导入、GM 终生字段修改与成长确认都携带并校验 `expectedVersion`；非法 `sheetData` 返回稳定的 400 校验错误，而不是 500。
6. **GM 差异同步可交付**：补 GM 的差异预览、字段选择和同步 UI；成功后向团内发送刷新，不再只有无人可调用的后端接口。
7. **公开卡按摘要投影**：开启“公开队友人物卡”时，队友/OB 只收到姓名、时代、年龄、职业、九属性、全部标准/自定义/专攻技能，以及 HP/MP/SAN 上限、MOV、DB、体格等衍生摘要；背景与立绘继续走现有独立快照字段。武器、护甲、装备、资产明细、法术、神话典籍和第三类接触仅本人与 GM 可见。投影只作用于团内 WS 快照/事件，主卡 REST 与导入响应本来就仅对所有者或授权 GM 开放，返回完整卡。投影由规则模块在服务端完成。关闭公开时仍只有本人与 GM 可见。
8. **显式同步同时重算派生上限**：GM 确认同步 sheet 时，按团内新快照重算 HP/MP/SAN 上限；HP/MP 保留 `旧上限 - 旧当前值` 的已损失点数，SAN 保留当前值且只在新上限更低时钳制。状态标记、成长和其他团内数据不变。所有上限与当前值变化必须先出现在同步预览中，确认后一次提交并广播刷新；未经显式同步不发生任何变化。

## 6. 前端交互与完整流程

现有“资料与表情”弹窗升级为宽幅人物编辑器，以现有 Tabs、Input、Select、Button、Table/Card 等组件组织：

1. 资料与表情：保留现有行为。
2. 属性与职业：九属性、年龄/时代/职业、本职技能与点数参考、衍生数值和年龄建卡提示。
3. 技能：完整目录、搜索、专攻与自定义技能，直接编辑当前值并显示半值/五分之一值。
4. 战斗与装备：武器、护甲和装备，武器关联技能并显示三档阈值。
5. 资产：信用评级、生活水平、建议资产和实际资产。
6. 法术与神话：法术消耗、神话典籍和第三类接触数值记录。

保存沿用现有 REST 与乐观锁；409 显示中文冲突提示并要求基于最新版本重试。数值保存成功的提示明确说明已提交审核的版本需要重新审核。团内只读人物卡按观察者投影展示摘要，本人与 GM 可查看完整数值；点击技能或武器关联技能仍只提交技能标识，不传目标值。

完整玩家流程一并覆盖：

- 新建人物后直接打开完整编辑器。
- 编辑现有主卡并保存完整字段。
- PL 工作台复用 Excel 导入弹窗，调用已有 `/pl/characters/import/*` 接口。
- 邀请链接的新人物提交复用规则编辑组件，不再只能提交默认 50 属性空卡。
- GM 编辑九属性时记录审计，所有编辑使用乐观锁。
- GM 在团内人物面板打开主卡差异预览，选择资料/数值字段并同步，在线客户端收到刷新。

## 7. 服务端与 Excel 导入

- CoC 规则实现提供统一解析、公开投影、技能目标值、衍生状态和成长修改所需的纯函数；通用人物用例不硬编码任何 CoC 字段或公式。
- 新团/新人物入团使用修正后的 HP、MP 与 SAN 上限推导；既有团状态不被追溯改写。
- 审核、入团、认领与创建团的查询路径统一检查审核版本，不能只在一个同步预览里展示 `staleReview`。
- 服务端保存时保留追加式人物版本；GM 的九属性差异同时追加审计。并发写入不能静默覆盖。
- Excel 导入沿用 RuleSystem 入口，支持现有简单表格与已确认的真实半自动模板 `人物卡`/`简化卡` 布局：正确识别工作表、姓名位置、当前值列、专攻、职业、年龄、资产、武器等已支持字段。
- 解析结果同时保留“明确出现的字段路径”和完整预览卡；暂存记录保存这份规则专属导入补丁，而不是靠比较默认值反推用户表格缺少哪些字段。确认更新时由规则实现把补丁合并到最新主卡。
- 对真实模板按明确列映射读取，不让职业列表或附表抢先提供错误数值；超过 Z 的单元格坐标正确生成。
- 新建人物按导入结果和空卡默认值创建。更新已有人物时采用明确字段合并：表格实际包含且解析成功的字段覆盖，未涉及的武器、资产、法术、神话记录及其他字段保留；解析失败的字段不能覆盖旧值。预览逐项列出将覆盖、保留和新增的内容，用户确认后才以 `expectedVersion` 一次保存，不逐字段发送多次写入。
- 无法可靠识别的列进入既有 warnings，不静默编造数值；无效值不能确认入库。已有简单表格导入行为保持可用，但更新已有卡不再因表格缺少新版字段而清空旧数据。
- 真实本机 Excel 用于实际验证；仓库自动化测试使用独立生成的同布局测试工作簿，不依赖本机绝对路径或复制用户文件。

## 8. 测试与验收

按 TDD 先写失败测试，再实现：

1. Shared/规则纯函数：schema 有效与无效输入、旧卡规范化、完整技能目录与专攻、公式边界、技能超过 100%、DB/体格各档、MOV 相等与年龄修正、信用评级和两时代资产表。
2. 服务端规则：SAN 上限、奖励骰成长排除、信用评级/克苏鲁神话成长排除、公开投影不泄漏私密字段、成长与终生字段写回保留完整卡。
3. 服务端集成：PL 从真实路由保存完整卡并追加版本；非所有者失败；非法数值返回 400；旧 `expectedVersion` 返回 409；审核过期不能批准或入团；主卡变化不影响团快照和鉴定，GM 显式同步后才更新；同步预览和提交正确重算上限、保留 HP/MP 损失并钳制 SAN；GM 属性修改产生审计。
4. 客户端组件：完整编辑往返、专攻/自定义技能/武器/法术增删、派生值实时更新、PL 与 GM 使用各自 API、冲突提示、非法输入不可保存、完整字段不会因保存而丢失。
5. Excel：简单表格和真实布局的姓名、当前值、专攻、资产与武器导入，未知列警告、无效值拒绝入库、覆盖更新冲突；已有卡合并时仅覆盖明确字段，未提供字段保留。
6. 浏览器端验收：玩家实际修改属性、专精技能、武器和资产，保存后刷新仍在；未同步团的鉴定使用旧快照，GM 同步后使用新值；队友收不到私密资产与神话字段。
7. 对本次 TypeScript 改动运行 Biome（若仓库仍无配置则报告阻碍），并运行相关测试、`bun run typecheck`、`bun run check:boundaries` 与 `bun run build:client`。

完成标准是玩家无需 GM 或 Excel 即可建立并维护完整官方数值卡，完整玩家/GM 流程可用，所有公式和权限边界与上述规则一致，且版本、审核、历史、导入和团内快照行为均有集成测试证据。
