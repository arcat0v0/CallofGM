## F1 场景切换后新背景永不显示（SceneBackdrop 交叉淡入竞态）
- 文件: apps/client/src/features/session-stage/scene-backdrop.tsx:19-34
- 现象: GM 控制台切场景后舞台仍显示上一张（首次切换则为全黑）。原因: effect deps 含 front；setFront(src) 触发重渲染 → effect cleanup 取消刚排的 rAF，setFrontVisible(true) 永不执行；同时 back 的清理 timer 也被取消，旧图永久残留。
- 复现: 控制台 → 场景切换 → 新场景图 opacity 恒为 0，back 图 opacity 1。
- 影响: 产品核心（场景同步换装）视觉上完全失效；同一竞态也命中「中途加入的玩家」——第二个玩家进团时舞台背景 opacity 恒为 0，只剩纯黑，直到他手动触发一次换景。

## F2 无立绘的角色完全无法发送「角色扮演」消息（默认 expressionKey 被服务端拒绝）
- 文件: apps/client/src/features/play/composer.tsx:58-64,86-90；apps/server/src/modules/chat/application/commands.ts:114-125
- 现象: 玩家认领的 PC 没有任何立绘时，composer 仍以 expression="default" 发送 roleplay 消息 → 服务端 portraitExists 失败 → command:rejected「Expression portrait not found for this character」，消息根本入不了队列。任何新建（无立绘）PC 在演绎时间/自由演绎阶段都无法发言。
- 复现: 新建 PC → 认领 → 阶段切到演绎时间 → 发言 → toast 报错，DB 无新消息行。
- 影响: 阻塞级。产品主流程（演绎发言经队列）对未上传立绘的角色 100% 失效，且报错文案是英文内部错误。

## F3 舞台对话气泡与立绘状态条重叠
- 文件: apps/client/src/features/session-stage/portrait-layer.tsx:30-36（bottom-24 / compact bottom-14）与 dialogue-box 定位（desktop-scene.tsx:47 `bottom-[36px]`）
- 现象: 桌面端立绘层底部距 96px，对话框底 36px 且高约 100px，两者在 96–136px 区间重叠；实际截图里最新对话气泡直接盖住了说话角色的 HP/MP/SAN 状态条与名牌。

## F4 自由讨论阶段「角色扮演」通道静默被改写、UI 无任何提示

## F5 「人物卡无技能」时默认空卡的鉴定必然失败（技能目录回退只在前端）
- 文件: apps/client/src/lib/coc-live.ts:15-23；apps/server/src/rules/coc7e/index.ts:145-156
- 现象: 新建人物（新建人物弹窗只写九属性，skills={}）后，前端 skillKeysFor 回退到完整技能目录，把「侦查」等技能列进骰盘/侧栏下拉；但服务端 getSkillTargetValue 只查已有 skills/attributes，返回 null → SkillNotFoundError「Skill or attribute not found on character sheet」。GM 侧栏默认 skill 就是「侦查」，所以对任何新建人物点「鉴定」或「请求」都直接失败。check:request 因此连一条 check_requests 记录都写不进。

- 影响: 产品要求「GM 可对任意角色发起鉴定」，对新建人物完全不可用；且客户端会显示不存在的技能。

## F48 命令去重缓存只按 commandId 索引（不含发起者），跨身份复用同一 ID 会「假成功」
- 文件: apps/server/src/modules/realtime/session-command-executor.ts:57-71,96-109（cachedReplies: sessionId → commandId → reply）

## F84 `resetHttpLimits()` 是一个危险的全局后门：任何 import 它的测试文件都会关掉整个进程的限流
- 文件: apps/server/src/platform/security/http-limits.ts:8-14（`process.env.COGM_SKIP_RATE_LIMIT = "1"` + 全部 limiter.reset()），rate-limiter.ts:24 检查该环境变量后直接放行。
- 实际调用: 5 个 contract 测试文件的 beforeAll 都调用 `resetHttpLimits()`；这些测试与生产共用同一构造路径，只要测试代码在生产进程（或同进程的其他服务）里被 import，限流即全局失效。
- 影响: 低概率但高风险的「测试辅助代码进入生产路径」；建议把 limiter 实例注入化（跟随 Container），而不是进程级 env 开关。

## F86 Excel 关键属性缺失时的行为是「填默认 50 + 记 error」，但 errors 非空时 confirm 直接拒绝，玩家属性无法修正

## F87 Excel 解析的边界行为: 姓名匹配用 includes 容易误命中且失败是静默的
- 代码: excel-parser.ts:65-77 —— nameQueries 用 `text.toLowerCase().includes(q)`，任何包含「姓名」二字的单元格（如「玩家姓名」）都会触发；「name」也一样。
- 触发条件: nameVal 是右侧或下一行第一个非空格 → 若表格把「姓名」和数值同行排版（B1=力量 60），会把「力量 60」之类文本当名字。
- 复测: 构造的表格 `A1=姓名 B1=张三` 正常解析出「张三」，常规路径 OK；姓名取值用 `includes` 命中后取右侧/下一行第一个非空格，遇到「玩家姓名 / 调查员姓名」分列的表格会取错列，且不产生任何 warning（errors 为空）。
- 影响: 中低。两段式导入有预览页兜底，错误名字可以被 GM 发现；但匹配失败是静默的，建议对「姓名来自 includes 命中」的场景打 warning。

## F88 媒体上传的 purpose 是自由字符串，不做枚举校验
- 文件: apps/server/src/modules/media/application/upload-media.ts:51（`input.purpose || "general"`，无白名单）
- 复测: `POST /media/upload` 带 `purpose=nonsense` → 200，DTO 原样回显 `purpose:"nonsense"`；而 MIME 类型校验是有的（text/plain → 400 UNSUPPORTED_MIME_TYPE）。
